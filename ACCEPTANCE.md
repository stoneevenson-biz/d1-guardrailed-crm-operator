# D1 acceptance criteria → tests

Every criterion maps to named tests in `tests/test_acceptance.py` and to at least one planted defect in
`proof.py` that must turn those tests red.

| AC | Criterion | Tests | Defects that prove it |
|---|---|---|---|
| AC1 | Reads (`crm.search_contacts`, `crm.get_contact`, `crm.list_pipeline`) run without approval, change nothing, and are logged. The agent's search text is data, never SQL. | `test_ac1_*` | `read-sql-injection` |
| AC2 | A tag or stage write without an approval token is not executed. The agent gets `needs-approval` with the exact scope a human would approve (action, contact, value). | `test_ac2_*` | `write-no-token` |
| AC3 | A human's token lets through exactly its scope: the named action, the listed contacts, the listed values. Anything else is `out-of-scope:action`, `:contact` or `:value`. | `test_ac3_*` | `scope-action`, `scope-contact`, `scope-value` |
| AC4 | Approvals are time-boxed: refused from the expiry instant on (`approval-expired`). A human cannot issue one longer than 15 minutes, zero-length, or with a non-integer lifetime. | `test_ac4_*` | `expiry-units`, `expiry-boundary`, `ttl-cap` |
| AC5 | Approvals are use-limited: after `max_uses` allowed calls the token is `approval-used-up`, so a replay is refused. At most 3 uses per approval. The count comes from the audit log. | `test_ac5_*` | `replay` |
| AC6 | Tokens cannot be forged, altered or self-issued: a garbage, differently signed or edited token is `bad-token`; only listed human approvers can grant; an approval must name real contact ids and non-empty values; a policy that lists the agent as an approver is refused at start-up; sends, deletes, reads and unknown tools can never be approved; the signing key and the tokens never appear in the log or the agent's tool menu. | `test_ac6_*` | `token-signature`, `self-approve`, `grant-send`, `grant-scope` |
| AC7 | Outbound SMS and email are always refused (`never:outbound`), with no token, with a write token, and even with a correctly signed token that names the send. The simulated outbox stays empty. | `test_ac7_*` | `send-with-approval` |
| AC8 | Deletes are refused (`never:destructive`), with or without a token. Any tool not classified in the policy is refused (`never:unlisted-tool`), including one an engineer adds later and forgets to classify, and it is not advertised to the agent. | `test_ac8_*` | `default-allow` |
| AC9 | Arguments must be exactly the tool's (names, exact types, ids between 1 and 2^31−1, text of 1–500 printable characters that is valid UTF-8); the contact must exist; tags must be whole-string slugs; stages must be in the pipeline. This holds even when a token names the bad value. A check that crashes is a logged refusal (`policy-error:…`), never an unlogged crash. | `test_ac9_*` | `stage-validation`, `control-chars`, `id-range` |
| AC10 | Every decision is in the audit log before anything runs: allows, refusals, approval requests, grants, refused grants, declines, protocol violations. The log is a separate store from the CRM, rejects UPDATE and DELETE, and is hash-chained: an edit or a deleted row fails `verify()` even after someone drops the triggers, and a truncation fails it against a head recorded earlier. If the decision cannot be logged, nothing runs (fail closed). Text that is not valid UTF-8 is logged escaped, and the agent's arguments are logged up to 2,000 characters. | `test_ac10_*` | `audit-denials`, `audit-append-only`, `audit-chain`, `audit-fail-open`, `audit-unicode`, `audit-size` |
| AC11 | The agent runs in its own process, in Python's isolated mode, inheriting nothing from the parent's environment (it sees only the OS/runtime locale defaults): no keys, the gateway's code not on its import path, and no handle to the CRM, the log or the signing key. It can only send a tool call, an approval request, a wait, a well-formed probe report or done, each at most 64 KB; anything else (for example "grant", a self-made "approval", bad JSON, bad UTF-8, deep nesting, an oversized line) is refused and logged, and the session carries on. Approval requests go to a human, who may decline. A looping agent is stopped by a message budget; a session that ends without "done" is logged. This is process separation, not an OS sandbox (README, Honest limits). | `test_ac11_*` | `agent-env-leak`, `agent-sys-path`, `pipe-limit` |
| AC12 | The one-command demo ends exactly as scripted: 17 decisions in order; the only CRM change is one approved tag; the outbox is empty; 5 contacts remain; the chain verifies. No API key and no network are needed. Text that came from the agent or the CRM is printed escaped and capped, so it cannot fake a line of the demo's output (including the audit listing). | `test_ac12_*` | `demo-escape`, plus every defect above that changes the scenario |
| AC13 | Proof hygiene: no network or model-SDK imports; the agent side imports only `json`, `os`, `sys`, `importlib.util`; every phone number is in the fictional 555-01xx range; no email addresses; every fixture carries the synthetic label; README and ACCEPTANCE open with the verbatim label; a LICENSE ships. | `test_ac13_*` | — (static checks) |

Out of scope, on purpose: a real CRM API, a real model, per-field write rules beyond tags and stages, approval UIs,
multi-tenant policy, shipping the log off-box. Those are what a paid build scopes, not what this demo shows.
